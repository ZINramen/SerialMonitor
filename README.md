# 장비 측정 모니터 (Serial Monitor)

장비에서 실시간으로 올라오는 측정값을 받아 **파싱 → 판정 → 화면 표시 → 기록**까지 처리하는 Windows 데스크톱 프로그램입니다.

C# / .NET 8 / WPF로 만들었고, 외부 차트 라이브러리 없이 그래프까지 직접 그렸습니다.

---

## 만든 이유

전자부품 검사 장비용 소프트웨어가 어떤 구조인지 직접 확인해보고 싶었습니다.

장비가 손에 없는 상태에서 시작해야 했기 때문에, **통신 계층을 인터페이스로 분리하고 가짜 장비(시뮬레이터)를 먼저 만들어 붙이는** 방식으로 개발했습니다. 결과적으로 이 선택이 가장 큰 도움이 됐습니다. 실제 장비는 일부러 고장나게 만들 수 없지만, 시뮬레이터는 유실·CRC 오류·무응답을 정해진 확률로 섞어 보낼 수 있어서 예외 처리를 매번 같은 조건에서 검증할 수 있습니다.

---

## 동작 구조

```
 ┌────────────┐   bytes    ┌──────────────┐  frames  ┌──────────────┐
 │  장비 /    │ ─────────▶ │  FrameParser │ ───────▶ │ DeviceSession│
 │ 시뮬레이터 │            │  경계·CRC    │          │ 판정·집계    │
 └────────────┘            └──────────────┘          └──────┬───────┘
      ▲                                                     │ 큐에 적재
      │ 명령(Ping/Start/Stop)                               ▼
      └──────────────────────────────────────────  ┌─────────────────┐
                                                   │  수신 스레드     │
                                                   └────────┬────────┘
                                                            │ 40ms마다 꺼냄
                                                            ▼
                                   ┌────────────────────────────────────┐
                                   │ UI 스레드 — 그래프 · OK/NG · 통계   │
                                   └──────────────┬─────────────────────┘
                                                  ▼
                                            CSV 원본 기록
```

### 핵심 설계 두 가지

**1. 수신 주기와 화면 갱신 주기를 분리했습니다.**

수신은 전용 스레드에서 돌면서 받은 값을 큐에 넣기만 하고, 화면은 40ms(초당 25회)마다 쌓인 값을 한꺼번에 꺼내 갱신합니다. 값이 들어올 때마다 화면을 그리면 초당 수백 번 렌더링이 일어나 UI가 멈추는데, 사람 눈은 그 차이를 구분하지 못합니다.

화면에 그리는 점은 가로 픽셀 수에 맞춰 줄이지만, **CSV에는 받은 값을 하나도 빠뜨리지 않고 전부 기록합니다.** 화면은 간추려도 되지만 기록은 빠지면 안 되기 때문입니다.

**2. 무응답을 예외가 아니라 정상적으로 일어나는 상황으로 다룹니다.**

타임아웃 → 재시도 3회 → 그래도 응답이 없으면 연결을 끊고 상태를 표시한 뒤 재연결을 시도합니다. 재시도는 **몇 번을 보내도 장비 상태가 달라지지 않는 명령(Ping)에만** 적용합니다. 장비를 움직이거나 설정을 바꾸는 명령은 중복 수행되면 위험하므로 일련번호로 막아야 합니다.

## 통신 프로토콜

```
 +-----+-----+-----+-----+----------------+---------+-----+
 | STX | LEN | SEQ | CMD |    PAYLOAD     |  CRC16  | ETX |
 | 02  |  1  |  1  |  1  |   LEN bytes    | 2 (LE)  | 03  |
 +-----+-----+-----+-----+----------------+---------+-----+
                  CRC 계산 범위: LEN ~ PAYLOAD 끝
```

| 필드 | 왜 필요한가 |
| --- | --- |
| `LEN` | 시리얼·TCP는 바이트 흐름이라 패킷 경계가 없습니다. 길이가 있어야 어디서 끊을지 알 수 있습니다. |
| `SEQ` | 0~255 순환. 번호가 건너뛰면 유실, 같은 번호가 또 오면 중복입니다. |
| `CRC16` | 중간에 깨진 데이터를 걸러냅니다. 단순 체크섬보다 버스트 오류 검출력이 좋습니다. |
| `STX`/`ETX` | 쓰레기 바이트가 섞였을 때 동기를 다시 잡는 기준점입니다. |

측정 페이로드(9바이트)는 채널(1) + 장비시간 ms(uint32) + 값(int32, 1/1000 단위)이며 **전부 리틀 엔디안**입니다. 값을 실수가 아니라 정수로 보내는 이유는 장비 쪽 MCU에서 부동소수점이 느리거나 없는 경우가 많고, 정수로 보내면 양쪽 해석이 어긋날 일이 없기 때문입니다.

## 만들면서 막혔던 것

**가장 어려웠던 건 통신 자체가 아니라 패킷 경계를 나누는 일이었습니다.**

처음에는 한 번 읽은 바이트를 그대로 한 프레임으로 해석했는데, 실제로는 프레임이 반만 와 있거나 두 개 반이 붙어 오는 경우가 섞여서 계속 깨졌습니다. 받은 바이트를 버퍼에 쌓아두고 완전한 프레임이 만들어질 때마다 꺼내는 구조로 바꿔서 해결했습니다.

**CRC가 틀린 프레임을 통째로 버렸더니 멀쩡한 프레임까지 같이 사라졌습니다.** 앞에서 STX로 본 바이트가 사실은 페이로드 안의 `0x02`였던 경우였습니다. 지금은 한 바이트만 버리고 다시 STX를 찾습니다. 이 동작은 테스트로 고정해 뒀습니다(`깨진_프레임_뒤에_오는_정상_프레임은_살린다`).

## 테스트

```bash
dotnet test
```

24개 테스트가 통과합니다. 통신에서 실제로 겪는 상황을 그대로 재현합니다.

| 분류 | 확인하는 것 |
| --- | --- |
| 프레임 파서 | 반으로 잘려 들어옴 / 여러 개가 붙어 옴 / 바이트 하나씩 들어옴 / 쓰레기 바이트 섞임 / CRC 오류 / 페이로드에 STX 포함 |
| 측정값 | 직렬화 왕복, 리틀 엔디안 바이트 순서, 잘못된 길이 거부 |
| 판정 | 상·하한 경계값 포함 여부 |
| 통합 | 정상 조건 무오류 수신 / 고장 주입 시 유실·CRC 집계 / 기준 이탈 NG 판정 / 무응답 시 타임아웃·재시도 |

## 실행

```bash
dotnet run --project src/SerialMonitor.App
```

장비가 없어도 **시뮬레이터 모드**로 바로 실행됩니다.

- **고장 주입** 체크박스 — 유실·CRC 오류·쓰레기 바이트·무응답을 일부러 섞습니다
- **CSV 기록** 체크박스 — `내 문서/SerialMonitor/` 에 원본을 전부 남깁니다
- **실제 시리얼** — USB-시리얼 변환기나 `com0com` 가상 포트로 실제 통신 테스트

## 구성

| 프로젝트 | 내용 |
| --- | --- |
| `SerialMonitor.Core` | 프로토콜·파서·CRC·장비 연결·수신 세션·판정·CSV 기록. UI를 전혀 모릅니다 |
| `SerialMonitor.App` | WPF UI (MVVM), 직접 그린 추이 그래프 |
| `SerialMonitor.Tests` | xUnit 테스트 24개 |

`IDeviceLink` 인터페이스 하나로 실제 시리얼(`SerialDeviceLink`)과 가짜 장비(`SimulatedDeviceLink`)를 갈아끼웁니다. 실제 장비가 생기면 구현체만 바꾸면 되고 위쪽 코드는 바뀌지 않습니다.
